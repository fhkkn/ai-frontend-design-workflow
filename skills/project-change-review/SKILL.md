# 项目改动审核

审核本轮改动是否必要、符合需求且有证据支持。默认只读：不修复、不重构、不更新项目记录、不提交、不推送、不发布，也不代替用户批准合并。检查命令先看定义，避免自动修复、快照更新或外部写入；需要生成临时产物时使用获准的隔离位置。无法安全运行的检查明确记为未验证。

## 确定本轮范围

读取用户本轮需求、已确认决定及适用项目规则，复用已有任务、状态和验收记录，不要求另建模板。记录改动前基线与当前审查版本：干净起点可用提交号；起点已有未提交内容时，需使用改动前快照或补丁及归属说明，不能把 HEAD 当作完整基线。

直接查看实际差异、新增文件和必要的关联上下文，不以实现者总结代替检查。Git 项目同时检查暂存、未暂存和未跟踪内容；通常先读 status，再按明确基线读取 diff，并打开本轮新增文件。按项目规则辨认被忽略但属于交付的文件，不遍历私人目录。无 Git 时比较明确的前后快照。清单不能替代同一文件内的差异归属判断。

有其他任务或用户改动时，先核对起始记录与本轮归属；无法分离的部分标为待核实，继续可确定部分，不能将所有工作区差异归给本轮。缺少基线、需求或关键证据时说明具体限制，只在影响判断时询问，不能给虚假通过结论。审查中版本变化时重新核对差异与证据对应关系。

## 沿差异检查

- **必要性与维护成本：** 新文件、抽象、依赖、步骤是否解决当前需求？已有实现是否足够？指出重复事实来源或重复机制的实际维护成本；不能仅因新增文件或抽象便判错。
- **事实与证据：** 对照代码、配置、接口定义和实际验证输出核验功能、依赖、API、约束及完成声明。区分观察、推断和实现者陈述。缺少日志不等于证明检查未运行；有相反证据才确认虚报，否则列为待核实。未执行不能记通过，自查不能称独立评审。
- **任务范围：** 将改动关联到需求或必要依赖关系。允许可解释且可验证的跨文件联动；无关重构、额外功能、全仓格式化需指出具体偏离与影响。旧问题只在本轮引入、放大或直接阻断本轮目标时作为本轮缺陷，否则注明原有状态，避免全仓整顿。
- **关联影响与回归：** 沿受影响调用方、接口、共享规则和状态读取必要上下文。前端项目按差异关注核心操作、数据与状态、接口契约、共享组件、响应式、键盘和基础可访问性；使用项目已有且相关的检查，不预设框架、目录或命令。执行相关检查并记录版本、命令、结果和证据；环境不具备时说明限制。静态截图不能证明交互有效，构建通过不能证明产品或视觉完成。
- **设计约束：** 检查是否违反已确认规范；审美判断交给项目既有视觉评审流程。个人风格偏好不是工程缺陷，不为稳妥抹平有意的设计个性。可观察的可用性问题仍需报告。

## 给出可复核结论

先写实际范围、基线、审查版本和审查者身份（实现者自查或实际独立评审），再报告发现与验证限制。默认直接在回复中交付；需要持久化时复用获准的现有记录。私人资料、聊天、凭据、本机路径或校准记录不得进入公开内容。

按“确认的问题／待核实风险／非阻断建议”区分，空类别可省略，允许零发现，不凑数量。每条包括文件与行号（删除内容标明基线位置）、可观察证据、对应需求或约束、实际影响、优先级和最小修复建议。无法定位或证实的风险不包装成已确认缺陷；条件性影响写明触发条件。

优先级按实际影响：P0 紧急严重损害；P1 核心目标或关键契约受损，应优先修复；P2 局部缺陷或具体维护成本；P3 非阻断改进。不要为风格偏好或未经证实的可能性提高等级。

结论使用：

- **通过：** 本轮范围与归属明确，相关必要验证充分，未发现需修改问题；仅对已审查范围负责。
- **需要修改：** 有确认且需处理的问题，仍须列出未验证部分。
- **证据不足：** 无法判断关键范围、事实或行为，列出最少需要补充的证据；零发现不等于通过。

复核修复时保留同一改动前基线，查看更新后的完整本轮差异、修复及必要关联影响。旧结果仅证明旧版本；重跑受新改动影响的检查，不用旧通过结果为新版本背书。
